# Database foundation

Revision `0001_foundation` creates users, immutable setting-version records with a current-version pointer, audit events and heartbeats. No trading approval, broker state or execution tables exist in Phase 1.

Provision the roles first through the repository's explicit setup script: `trd_owner` is NOLOGIN; only `trd_migrator` is its member. The owner requires USAGE/CREATE on the target database's public schema. Runtime roles are `trd_api`, `trd_collector`, `trd_ai`, `trd_risk` and `trd_maintenance`; they have no owner membership, schema CREATE or base-table mutation privileges.

Set `MIGRATION_DATABASE_URL` to the dedicated `postgresql+psycopg` migrator credential and run `python -m alembic upgrade head`. Migrations switch to `trd_owner`, making that NOLOGIN role the object owner. Runtime processes receive only their own database URL. Migration/bootstrap credentials never enter normal service environments.

Explicit bootstrap uses `python -m backend.application.bootstrap`, with `ENVIRONMENT_ID`, `MIGRATION_DATABASE_URL`, `ADMIN_BOOTSTRAP_EMAIL` and `ADMIN_BOOTSTRAP_PASSWORD`. The operator supplies a password of at least 16 characters; no public default exists. Bootstrap hashes with Argon2id, seeds paper mode and disabled automation/live flags, and commits defaults plus audit in one transaction. Repeating bootstrap preserves existing passwords/configuration and does not promote an existing VIEWER or repair inconsistent history silently.

API reads are restricted to `api_users`, `api_settings`, `api_audit_events` and `api_heartbeats`. These projections omit password hashes, internal setting keys and raw audit details. Phase 1 exposes no unauthenticated administrative endpoints. Future auth/settings work must introduce reviewed capability-specific grants/functions, not grant the API unrestricted table mutation.

All runtime identities may call `record_service_heartbeat` for their own service. This narrowly scoped SECURITY DEFINER function fixes its search path, puts the temporary schema last, qualifies table names and derives identity from `session_user`: `current_user` would become the owner inside a definer function. Direct heartbeat insert/update is denied. Heartbeats are operational liveness, not broker/account/risk authority. These controls follow PostgreSQL's [definer-function security guidance](https://www.postgresql.org/docs/17/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY) and [session identity semantics](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-INFO-SESSION).

Future functions created by `trd_owner` receive no implicit PUBLIC EXECUTE. This revocation is global within the database: PostgreSQL's [default-privilege semantics](https://www.postgresql.org/docs/17/sql-alterdefaultprivileges.html) make schema defaults additive, so a schema-scoped revocation would not remove the implicit global grant. New callable capabilities need explicit reviewed grants. These security defaults remain in place after downgrading the foundation tables.

Integration tests require an explicit `TEST_ADMIN_DATABASE_URL` for a PostgreSQL 17 test server and all six scoped role URLs. Fixtures create only random `trd_test_<uuid>` databases and drop only those databases. Tests cover fresh/repeated upgrade, downgrade/re-upgrade, owner identities, idempotent/concurrent bootstrap, rollback, password redaction, safe projections and actual SQL permission failures. Downgrade removes foundation data and is for disposable tests or explicit operator recovery; regular deployment uses forward migrations.

Sessions/connections are local to each synchronous operation. Engine pools are safe to share; no mutable SQLAlchemy Session crosses threads or async network waits. Database loss or schema mismatch fails readiness. SQL credentials and raw database exceptions must not be returned to a browser or written to ordinary service logs.
